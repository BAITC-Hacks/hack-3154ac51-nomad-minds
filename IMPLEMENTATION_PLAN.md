# План реализации «Аким на 5 часов»

## 1. Цель MVP

Собрать воспроизводимый AI-симулятор, в котором все команды получают одинаковые исходные данные и бюджет 100 условных единиц, выбирают ровно 5 городских мероприятий, а система:

- не допускает невалидный сценарий;
- детерминированно рассчитывает изменения по районам и Astana Quality of Life Score;
- показывает сильные стороны, риски и компромиссы;
- передаёт готовые числовые результаты в LLM только для объяснения и рекомендаций;
- позволяет повторить сценарий и сравнить результат с базовым состоянием.

Главный принцип: математическое ядро считает показатели без AI. LLM не придумывает числа, а объясняет рассчитанный результат.

## 2. Технологический стек

### Frontend

- Angular 22, standalone components;
- TypeScript в strict-режиме;
- Angular Signals для локального состояния симулятора;
- RxJS для HTTP и асинхронных операций;
- Angular Router для экранов;
- NG-ZORRO для таблиц, карточек, модальных окон, уведомлений и кнопок;
- Tailwind CSS + SCSS для компоновки и визуальных деталей;
- SVG-карта районов для стабильного офлайн-демо;
- ECharts или Chart.js для radar/bar chart, если библиотека будет добавлена.

### Backend

- FastAPI + Pydantic;
- чистый Python-модуль расчёта Score;
- JSON-файлы с исходными районами и каталогом мероприятий;
- API-провайдер LLM через отдельный адаптер;
- pytest для формулы, правил и API.

Для полностью воспроизводимого демо предусмотреть fallback-анализ на шаблонах: если LLM недоступна, пользователь всё равно получает объяснение на основе рассчитанных вкладов.

## 3. Архитектура

```text
Angular UI
  ├── Scenario Store (выборы, бюджет, статус валидации)
  ├── Scenario API service
  ├── страницы: Сценарий / Результаты / Сравнение / README
  └── визуализации карты и показателей
             │ HTTP /api
             ▼
FastAPI
  ├── Dataset repository
  ├── Scenario validator
  ├── Deterministic scoring engine
  ├── Contribution analyzer
  ├── LLM explanation adapter
  └── Scenario repository (in-memory/SQLite)
```

Поток данных:

1. Frontend загружает один зафиксированный датасет и каталог мероприятий.
2. Пользователь выбирает мероприятие и, если требуется, район.
3. Frontend мгновенно проверяет бюджет и базовые ограничения для UX.
4. Backend повторно валидирует сценарий как единственный источник истины.
5. Backend рассчитывает новые показатели, Score и вклад каждого решения.
6. LLM получает только структурированный расчёт и формирует объяснение.
7. Frontend показывает результат и сохраняет снимок сценария для сравнения.

Файлы должны иметь `datasetVersion`, чтобы сохранённые результаты можно было воспроизвести.

## 5. Правила сценария и расчёт Score

### Валидация

Сценарий валиден, только если одновременно выполнены условия:

1. Общая стоимость не превышает 100.
2. Выбрано ровно 5 решений.
3. Одно мероприятие нельзя выбрать повторно.
4. Для районного мероприятия район обязателен, для городского — отсутствует.
5. Не более 2 мероприятий из одного направления.
6. M1 и M3 несовместимы в одном сценарии.
7. M4 и M7 несовместимы в одном районе.
8. M5 и M13 несовместимы в одном районе.

Frontend должен блокировать очевидно невозможное действие до отправки, но backend обязан повторять все проверки.

### Эффекты

Горизонт моделирования — 8 кварталов. Для каждого эффекта применяется коэффициент реализации:

```text
realizationFactor = (8 - lagQuarters) / 8
appliedEffect = fullEffect * realizationFactor
```

Для районной меры эффект применяется только к выбранному району, для городской — ко всем районам. После основных эффектов добавляются фиксированные синергии:

- M1 + M2: T1 +2 в районе M1;
- M10 + M12: B1 +2 в районе M10;
- M5 + M6: E2 +2 в районе M5.

Каждый новый показатель ограничивается диапазоном 0–100.

### Районный и городской баллы

```text
D_d = 0.10*T1 + 0.10*T2
    + 0.09*E1 + 0.11*E2
    + 0.11*S1 + 0.11*S2
    + 0.09*B1 + 0.09*B2
    + 0.10*C1 + 0.10*C2

D_avg = Σ populationShare_d * D_d

Score = 0.7 * D_avg
      + 0.3 * min(D_d)
      - 1.0 * N_crit
```

`N_crit` — количество пар «район × показатель» со значением строго меньше 40 после применения всех эффектов. Базовый Score датасета — 52.56.

Результат округлять только для отображения. Внутренний расчёт выполнять с полной точностью, чтобы избежать расхождений между тестами и UI.

## 7. Экраны и пользовательский сценарий

### 7.1. Экран «Сценарий»

Композиция повторяет предоставленный референс:

- верхняя навигация и статус пользователя/команды;
- карточки «Бюджет» и «Решений принято»;
- список пяти районов с исходным баллом;
- интерактивная SVG-карта районов;
- каталог из 14 мероприятий с фильтрами по направлению;
- таблица выбранных решений;
- компактный блок предварительного результата.

Основное взаимодействие:

1. Пользователь выбирает мероприятие.
2. Для `scope = district` открывается модальное окно выбора района.
3. Система проверяет бюджет, повтор, лимит направления и конфликты.
4. Допустимое решение появляется в списке, бюджет и preview пересчитываются.
5. После пятого решения активируется кнопка «Рассчитать сценарий».

Ошибки должны объяснять причину и способ исправления: «M4 нельзя выбрать для Нуры, пока там выбрана M7» вместо общего «Ошибка».

### 7.2. Экран «Результаты»

- итоговый Score и изменение к базе 52.56;
- средневзвешенный городской балл;
- самый слабый район;
- число критических показателей;
- таблица «до / после / дельта» по районам;
- radar chart по пяти направлениям;
- список применённых синергий;
- вклад каждого мероприятия;
- AI-анализ: сильные стороны, риски, компромиссы и 2–3 рекомендации;
- кнопки «Изменить сценарий» и «Сохранить для сравнения».

### 7.3. Экран «Сравнение команд/сценариев»

Для MVP достаточно сравнивать локально сохранённые сценарии:

- название команды или сценария;
- затраченный бюджет;
- Score и дельта к базе;
- самый слабый район;
- охваченные направления;
- короткое резюме компромисса.

Если останется время, заменить локальное хранение на SQLite и добавить общий leaderboard.

### 7.4. Экран «README»

Кратко показать внутри приложения правила, формулу и трактовку показателей. Полный README остаётся в репозитории.

## 8. Backend API

Минимальный контракт:

```text
GET  /api/v1/dataset
     Возвращает бюджет, районы, показатели, мероприятия, веса и правила.

POST /api/v1/scenarios/validate
     Проверяет частичный или полный набор решений.

POST /api/v1/scenarios/calculate
     Повторно валидирует и возвращает детерминированный результат без LLM.

POST /api/v1/scenarios/analyze
     Принимает рассчитанный результат и возвращает AI-объяснение.

POST /api/v1/scenarios
GET  /api/v1/scenarios
     Опциональное сохранение и сравнение сценариев.

GET  /api/v1/health
     Проверка готовности backend и статуса AI-провайдера.
```

Разделение `calculate` и `analyze` важно: Score показывается даже при недоступной модели, а AI-запрос можно повторить отдельно.

## 9. AI-анализ

LLM получает JSON без персональных данных:

- базовый и итоговый Score;
- затраты и остаток бюджета;
- дельты районов и направлений;
- слабейший район и критические показатели;
- выбранные меры и их рассчитанный вклад;
- применённые синергии и оставшиеся пробелы.

Ответ должен проходить валидацию по схеме:

```json
{
  "summary": "...",
  "strengths": ["..."],
  "risks": ["..."],
  "tradeoffs": ["..."],
  "recommendations": [
    {
      "replace": "M...",
      "with": "M...",
      "reason": "..."
    }
  ]
}
```

Ограничения промпта:

- не пересчитывать и не изменять переданные числа;
- не утверждать причинность вне заданных эффектов;
- ссылаться на конкретные районы, показатели и решения;
- явно отмечать компромиссы;
- отвечать на русском языке;
- укладываться в короткий формат, пригодный для карточек интерфейса.

Шаблонный fallback строится по тем же полям: топ-3 положительных дельты, слабейшие показатели, непокрытые направления и самое выгодное допустимое улучшение.

## 10. План работ по этапам

### Этап 0. Фиксация контрактов — 1–2 часа

- перенести PDF-датасет в JSON без изменения значений;
- описать Pydantic-модели и TypeScript-интерфейсы;
- зафиксировать примеры запросов/ответов;
- добавить версию датасета и константу бюджета.

Результат: frontend и backend могут разрабатываться независимо по одному контракту.

### Этап 1. Расчётное ядро и тесты — 3–4 часа

- реализовать валидацию восьми правил;
- реализовать лаги, районные/городские эффекты, синергии и `clip`;
- реализовать районные баллы, городской средний и итоговый Score;
- вернуть подробные дельты и вклад мероприятий;
- покрыть pytest эталонными сценариями.

Результат: пример M7 Нура + M8 Нура + M10 Нура + M12 + M5 Сарыарка стоит 95 и даёт примерно 56.5.

### Этап 2. Каркас Angular и состояние — 2–3 часа

- настроить маршруты и lazy-loaded страницы;
- подключить HttpClient и обработчик ошибок;
- создать модели, API-сервис и `ScenarioStoreService`;
- реализовать восстановление состояния из `localStorage`.

Результат: приложение загружает реальный датасет и сохраняет выбранный сценарий.

### Этап 3. Основной сценарий выбора — 5–6 часов

- сверстать шапку, бюджет, районы и каталог;
- сделать выбор района для районных мер;
- реализовать добавление/удаление решений;
- показывать стоимость, направления и эффекты;
- блокировать превышение бюджета и конфликты;
- добавить доступные состояния hover/focus/disabled и responsive layout.

Результат: пользователь без перезагрузки собирает валидные 5 решений.

### Этап 4. Результаты и визуализация — 4–5 часов

- подключить `calculate`;
- показать Score, базу и дельту;
- построить таблицу динамики районов;
- добавить radar chart направлений;
- подсветить слабейший район, критические значения и синергии;
- сделать SVG-карту с выбором и визуальным изменением состояния.

Результат: изменение набора решений заметно меняет показатели и итоговый Score.

### Этап 5. AI и устойчивый fallback — 3–4 часа

- реализовать адаптер AI-провайдера;
- добавить структурированный промпт и JSON Schema;
- проверить числа и ссылки на меры после ответа;
- реализовать шаблонное объяснение при timeout/error;
- добавить отдельную кнопку повтора AI-анализа.

Результат: объяснение всегда доступно, а сбой AI не ломает демонстрацию.

### Этап 6. Сравнение и сохранение — 2–3 часа

- сохранять именованные снимки сценариев;
- показывать таблицу сравнения;
- добавить экспорт результата в JSON;
- при наличии времени — общий leaderboard через SQLite.

### Этап 7. README, QA и демо — 3–4 часа

- написать инструкции запуска frontend/backend;
- описать архитектуру, формулу, датасет и AI-ограничения;
- добавить `.env.example` и режим запуска без AI-ключа;
- проверить эталонный и ошибочные сценарии;
- выполнить unit/API/UI smoke tests;
- подготовить 3–5-минутный демо-сценарий.

- выбор ровно 5 решений;

- экран результатов с объяснением;
- README и запуск одной понятной последовательностью команд.

### P1 — повышает оценку

- SVG-карта и графики;
- сохранение и сравнение сценариев;
- структурированный AI-анализ с fallback;
- качественные тесты формулы и валидатора;
- Docker Compose для воспроизводимого запуска.

### P2 — только после стабильного MVP

- неожиданные городские события;

Неожиданные события не включать в основной Score хакатона без отдельного режима, иначе команды перестанут стартовать в одинаковых условиях.

## 12. Тестирование

### Backend unit tests

- базовый набор данных даёт Score 52.56;
- эталонный сценарий из датасета даёт около 56.5;
- лаги применяются с коэффициентом `(8-L)/8`;
- городская мера меняет все пять районов;
- районная мера меняет только целевой район;
- каждая синергия применяется один раз и в правильном районе;
- показатели обрезаются до диапазона 0–100;
- `N_crit` считает только значения `< 40`;
- все несовместимости и ограничения возвращают конкретную ошибку.

### Angular unit tests

- бюджет и остаток пересчитываются после добавления/удаления;
- шестое решение не добавляется;
- повтор и третья мера направления блокируются;
- городская мера не требует района;
- кнопка расчёта активна только для полного валидного набора;
- состояние корректно восстанавливается из `localStorage`.

### E2E smoke flow

1. Открыть новый сценарий и увидеть бюджет 100 и базовый Score 52.56.
2. Выбрать эталонные пять решений стоимостью 95.
3. Убедиться, что набор валиден и осталось 5.
4. Рассчитать результат около 56.5.
5. Получить AI-объяснение или fallback.
6. Заменить одно решение и убедиться, что Score изменился.
7. Сохранить оба сценария и сравнить их.

## 13. Definition of Done

Решение готово к сдаче, если:

- чистый клон запускается по README;
- frontend и backend имеют health/smoke-проверку;
- основной сценарий полностью проходит без ручного изменения данных;
- невалидный набор невозможно отправить, а API всё равно его отклоняет;
- Score совпадает с эталонными тестами;
- AI не участвует в арифметике и имеет fallback;
- интерфейс работает на ширине ноутбука и не ломается на планшете;
- в репозитории нет секретов, ключей и персональных данных;
- демонстрация укладывается в 3–5 минут.
